# Resident GPU Canny edge extraction

Date: 2026-10-13. Named slice: signed image gradients, suppression and complete
weak/strong edge connectivity on device, using the existing owned image model.

## API and execution

`canny_gpu(runtime, source, GpuCannyOptions)` accepts a borrowed resident
single-channel u8 `GpuImage` and returns an independently owned binary edge
image. It is exported by `spatialrust_gpu` and through `spatialrust::gpu` under
`gpu-image`. `canny_gpu_profiled` records optional pass timestamps, which remain
on device until explicit native collection. Thresholds default to 100/200,
aperture 3 and L1 comparison, matching CPU Canny. Dimensions and metadata remain.
RGB conversion and Gaussian smoothing are separate explicit caller operations;
Canny does not blur or move source images to CPU internally.

The threshold host preparation matches CPU validation/order: finite nonnegative
values, reversal swapping, aperture-7 division by 16, and floor after squaring
capped L2 thresholds. Large L1 values saturate to u32::MAX because every actual
gradient magnitude is smaller; this preserves CPU i64 comparisons. Only the
small 96-byte control uniform/coefficients is uploaded by a filter call.
The established image receipt excludes uniform controls from payload counters.

Aperture 3 computes paired signed Sobel gradients directly. Apertures 5/7 use
unrounded horizontal integer derivative/smoothing rows and a vertical pass.
Binomial kernels preserve the CPU arithmetic on u8 data. Aperture 7 scales by
1/16 with signed ties-to-even rounding before magnitude/direction comparison.
L1 absolute sums and squared L2 magnitudes fit the validated integer range.
No device f64, square root or shader floating-point rounding is required.

Classification uses the CPU TG22=13573 direction rule and asymmetric NMS ties:
horizontal/vertical magnitudes exceed the first neighbor and may equal the
second; diagonal magnitudes exceed both. Out-of-image comparison magnitudes
are zero. Low/high tests are strict. Private states encode suppressed/weak/
strong as 0/1/2; that private encoding differs from CPU workspace states, while
the public edge bytes agree.

Four forward neighbors (right, below and the two lower diagonals) enumerate
every undirected eight-neighbor edge between weak candidates. Monotone
atomic union uses the existing point-cloud connectivity algorithm's pattern:
path halving with atomicMin, then weak-CAS retry hooking only a current higher
root to a lower root. Every hook strictly decreases, preventing cycles/lock
ownership. There is no fixed iteration budget that truncates weak chains.
After the connect pass completes, weak roots are compressed. Each weak pixel
checks its immediate eight neighbors for a strong seed and flags its component
root. Strong pixels survive directly; weak pixels survive only when their root
is flagged. Any path from a weak pixel to a strong seed has a final weak vertex
next to a strong one, so this preserves complete CPU hysteresis without joining
strong-only regions. The final texture emits 0/255 red with all unused RGBA
components zero. Connectivity does not require host iteration, label readback
or CPU BFS.

Five ordered passes (aperture 3), or six (5/7), share one submission. Pixel
work uses up to 4096 flat workgroups and checked grid-stride tail advancement.
Private storage is 16*N gradient bytes, three 4*N state/parent/flag buffers,
and an 8-byte unused horizontal binding (3) or an 8*N horizontal buffer (5/7).
Peak private scratch is 28*N+8 or 36*N bytes, independently of edge density.
The largest binding is 16*N; total memory and graph contention still matter.
Individual device/storage/texture capacities reject unsupported images.

Receipts clone the source history, add named device stages and preserve exact
host/image payload bytes. Per-pass destination storage footprints sum to
44*N (3) or 52*N (5/7). Repeated in-place atomic updates/reads are not counted
as measured byte traffic; the generic receipt documentation now makes that
distinction explicit. All output/temporary storage remains on the originating
runtime, with submitted exclusive leases and existing bounded pool retention.
An explicit final image readback still uses padded RGBA rows.

Runtime ownership, positive grayscale dimensions, aperture/thresholds, signed
coordinate and u32 indexing, buffer/uniform sizes, five-storage-buffer/eight-
binding limits and workgroup dimensions are checked before cache/resource
allocation. Profiling reserves all five/six stages before work and requires
the correct timestamp-enabled runtime. Unsupported capacities propagate errors;
there is no CPU fallback or automatic placement. Existing CPU Canny, Gaussian,
Sobel and Vision-chain defaults remain unchanged. No production dependency,
core model or unsafe boundary is added; existing CPU Canny references are
enabled only in development dependencies.

## Validation

Six native Canny tests passed:

- 864 complete CPU comparisons, covering six geometries (1x1, 1x37, 37x1,
  2x3, 17x19, 65x33), four constant/noise/bar/low-contrast profiles, all three
  apertures, both norms and six threshold pairs including fractional, exact,
  reversed and f64::MAX values. All 367,056 edge bytes and metadata agree.
- 24 owned snapshots compared with independent direct 2D binary64 convolution
  from binomial coefficient formulas, integer direction/threshold references
  and BFS eight-neighbor components. Gradient words, classifications, minimum
  weak-component roots, strong-neighbor flags and final edges agree. One forced
  workgroup covers every pixel through grid strides. Copies are encoded before
  exclusive scratch recycling, avoiding observations of reused buffers.
- Eighteen connectivity-only masks cover no seeds, all weak candidates,
  diagonals, strips and disconnected components. Two 1025x1025 masks contain
  long serpentine weak paths, with a far-end strong seed and a broken-path
  variant. Complete roots, flags and output bytes match independent BFS;
  the graph reaches beyond the 4096-workgroup stride boundary.
- All 326,401 signed aperture-7 raw derivative values in [-163200,163200]
  match independent binary64 ties-to-even division by 16 on device.
- Exact scratch/uniform bounds and 14 reduced device limits reject bad
  dimensions/channels/apertures/nonfinite or negative thresholds. Invalid
  source runtime/options and profiler owner/capacity leave pool stats and
  Canny cache state unchanged.
- Strided ROI metadata, four concurrent callers, retained outputs after source
  recycling/runtime movement, dirty scratch reuse and timestamp stage/query
  receipts agree. A Gaussian/Canny/AI chain has one input upload and no
  intermediate image readback. Facade smoke covers all three apertures in a
  gray/Gaussian/edge/AI pipeline.

The complete native GPU-image library regression passed: 85 tests, with 14
intentional ignored measurement fixtures. All-feature/all-target GPU Clippy,
facade smoke, feature-free GPU and GPU-image WASM builds and formatting passed.

## Completed-call performance

Two sequential isolated native release surveys completed successfully. Backend
is Vulkan with a discrete device; no adapter model is recorded. Both surveys
report 12 default Rayon workers. CPU dispatch is otherwise unchanged and no
worker override is forced. The twelve cases use 256x192, 1920x1080 and
3840x2160 grayscale images; apertures 3/5/7; L1/L2; and seeded noise, tiled
bars and low-contrast profiles. Thresholds remain 100/200. No Gaussian or
color conversion is included in these Canny-only timers.

Each case receives three completed warmups per stage and 20 paired rounds.
The order rotates through four stages:

- CPU owned API: existing canny(), including output/workspace allocations,
  CPU gradient/classification/connectivity and the returned complete image.
- CPU into: existing canny_into() with a reused caller output/workspace.
  Aperture 3 uses the allocation-light path. Apertures 5/7 STILL call the
  CPU inspectable implementation and allocate their intermediates inside
  each timed call; their comparison is not an allocation-free CPU kernel.
- GPU full: upload/packing, uniform/control preparation, scratch/output
  acquisition, all five/six passes, completed image readback/unpacking,
  receipt copy and resource recycling. This returns the complete host image.
- GPU resident: already uploaded source, controls, scratch/output acquisition,
  all passes/submission and wait_idle completion. It excludes initial image
  upload, output readback and recycling; the output is downloaded and checked
  immediately afterward, before the next timed call.

Every warm/timed result matches CPU edge bytes and metadata exactly. Physical
upload/readback bytes and stage destination footprints are asserted. Resident
calls preserve the original upload and zero intermediate image D2H. Runtime
construction, pipeline compilation, input generation and independent output
checks occur outside timers. Resource acquisition and normal warm-cache/pool
behavior inside each API remain timed. No overlapping local builds, tests,
other benchmarks or statistical analysis ran during either survey.

Times are medians in milliseconds. Ratios are geometric means of 20 paired
baseline/GPU times. CPU API/full GPU compares complete host-image calls;
CPU into/resident GPU describes explicitly prepared input placement and the

For 1080p apertures 5/7, completed GPU host-image calls are 4.98-7.55x faster
than the current CPU API across the two surveys; prepared comparisons give
9.42-12.75x gains. At 4K aperture 5 the completed ratios are 6.60/13.55x;
aperture 7 gives 9.76/9.79x. The corresponding prepared ratios are 17.46-28.83x.
These gains include the current CPU larger-aperture allocation/inspectable
path costs and do not claim a comparison to a hypothetical optimized CPU path.
The small noisy 256x192 aperture-7 case gives 2.70-3.02x completed gains.

All measured aperture-3 completed calls are slower on GPU. Their CPU/GPU
ratios are 0.11-0.63: CPU is 1.6-9.2x faster when transfers are included.
Prepared 1080p results range from 0.93 to 2.65x; noise/low-contrast gains
are inconsistent between surveys, and one interval includes one. At 4K,
prepared aperture-3 GPU is slower than CPU into in both profiles/surveys,
with ratios 0.43-0.91. No automatic GPU placement is introduced, and no
blanket resident-compute gain is claimed.

Large-image wall times have substantial spikes. For aperture-7 4K, resident
medians differ from 16.560 to 61.090 ms, and full medians from 70.246 to
73.414 ms. Large scratch acquisition, bounded retention, scheduling and
completion are included in these timers; this evidence does not isolate which
caused the spikes. All samples, including adverse tails, remain in the paired
ratios/intervals. GPU pass-only times are not substituted for completed calls.

A 4K call requires a 132,710,400-byte gradient binding, 33,177,600-byte state/
parent/flag buffers and (5/7) a 66,355,200-byte horizontal binding. Private
scratch is 232,243,208 bytes (3) or 298,598,400 bytes (5/7), besides live
textures/control. Upload and final padded image D2H are each 33,177,600 bytes;
intermediate gradient/label data never crosses to CPU. Memory/device capacity
and existing pool budgets remain practical placement constraints. Reducing
private gradient storage is a possible follow-up; it is not implemented here.
